## 1. 工程概述

这是一个基于 .NET 8 的**分布式游戏服务器框架**，采用 “TCP + Protobuf Envelope” 长度前缀协议与客户端通信。多种服务角色（Directory / Login / Logic / Battle）由统一的 `ServerHost.dll` 启动，通过 `--service` 参数决定角色。

```
┌──────────────┐   TCP/Envelope    ┌─────────────────────────────────┐
│ Unity 客户端 │ ───────────────▶ │ ServerHost (--service login/...) │
└──────────────┘                   │   BaseGameServer 派生实例         │
                                    │   ├─ 强类型消息处理器               │
                                    │   ├─ 限流 / 黑名单                  │
       心跳(TCP/Envelope) ▲         │   └─ HeartbeatSenderService ──┐    │
                          │         └───────────────────────────────│────┘
                          │                                         │ 心跳
                  ┌───────┴─────────────┐                           ▼
                  │ DirectoryGameServer │ ◀───────────────────────────
                  │  ├─ HeartbeatHandler│   注册表(Memory / Redis)
                  │  └─ ServerQueryHandler
                  └─────────────────────┘
                          ▲ HTTP /api/routing/query
                  ┌───────┴─────────┐
                  │ ControlPlane    │  (Lit + Vite 运维 UI)
                  └─────────────────┘
```

## 2. 模块清单

| 项目 | 框架 | 职责 | 关键类型 |
|---|---|---|---|
| **Shared** | net8.0 | 协议（Protobuf 生成）、时间抽象、令牌签名 | `TokenSigner`、`TimeManager`、`envelope`、`HeartbeatRequest` |
| **Core** | net8.0 | 服务器框架内核 | `BaseGameServer`、`MessageHandling`、`MessagePipeline/*`、`Directory/*`、`Heartbeat/*`、`Diagnostics/*`、`Telemetry/*` |
| **ServerHost** | net8.0 | 进程入口、托管、HTTP 健康/管理端点、Redis 注册表 | `Program.cs`、`GameServerService`、`RedisServerRegistry`、`AdminConsoleHostedService` |
| **ControlPlane** | net8.0 (Web) | 运维 UI 宿主 | `Program.cs` + `web/control-plane-ui` (Lit) |

**核心能力**：可插拔服务注册表（内存/Redis）、负载/随机/轮询选择策略、每连接与每 IP 滑动窗口限流、黑名单、OpenTelemetry 指标与链路、Liveness/Readiness 健康检查、控制台 REPL + HTTP 管理命令、可注入的时间提供者（系统/偏移/手动）。

## 3. 请求生命周期（实际代码路径）

1. `BaseGameServer.AcceptLoop` 接受连接 → 黑名单/并发上限校验 → `HandleClient`。
2. `HandleClient` 读取 4 字节长度前缀（`BitConverter.ToInt32`，**小端**）→ 读 body → 限流校验 → `envelope.Parser.ParseFrom`。
3. envelope 写入 **Unbounded Channel**，由单一 `requestProcessor` 串行消费。
4. 按 `env.Type` 在 `_typedHandlers` 查找 `IHandlerInvoker` → `Invoke` → 反射读取响应的 `Success/Code/Message` → 映射错误码 → `WriteEnvelopeAsync` 回写。

> ⚠️ 注意：`MessagePipeline / AuthMiddleware / HandlerMiddleware / TelemetryMiddleware` **不在此路径上**——它们从未被调用（详见 §4.2）。

## 4. 严重问题（Bug / 与文档不符，建议优先修复）

### 4.1 🔴 心跳长度前缀字节序不一致——心跳实际不可用

- **发送端** `HeartbeatSenderService.cs:90`：
  ```csharp
  var lenBuf = BitConverter.GetBytes(System.Net.IPAddress.HostToNetworkOrder(envBytes.Length)); // 大端
  ```
- **接收端** `BaseGameServer.cs:584`：
  ```csharp
  var length = BitConverter.ToInt32(lenBuf, 0); // x64 小端，无 ntohl
  ```
- 服务器自身的响应写入 `WriteEnvelopeAsync`（`BaseGameServer.cs:401`）用的是 `BitConverter.GetBytes`（小端），与读取一致。**唯独心跳发送端用了大端**。
- **后果**：在小端机器（x64 Windows/Linux）上，心跳的长度字段被解析为一个巨大的数 → 触发 `BaseGameServer.cs:585` 的「非法或过大消息长度，断开连接」→ 心跳全部失败 → 注册表永远为空 → `/api/routing/query` 与 `ServerQueryHandler` 返回空列表。
- **修复**：发送端改用 `BitConverter.GetBytes(envBytes.Length)`（与全协议统一为小端），或两端统一改为网络字节序。**建议在协议层固定一种字节序并写测试锁定**。

### 4.2 🔴 鉴权中间件是死代码——客户端请求从未被认证

- `MessagePipeline`、`AuthMiddleware.UseAuth`、`HandlerMiddleware.UseHandler`、`TelemetryMiddleware.UseTelemetry` 全部定义齐全，但**全仓库无任何调用点**（无 `new MessagePipeline()`、无 `.UseAuth()`）。
- 真实分发路径 `BaseGameServer.HandleClient` 直接查 `_typedHandlers` 并调用，**绕过整个 pipeline**。
- `RequestServerContext` 携带了 `token`，但 `SetAuth(...)` **永不被调用** → 处理器侧 `context.Auth` 恒为 `null`。
- **后果**：登录令牌（`envelope.token`）从未被验签；任何携带正确 `type` 的报文都会被处理。README §7「客户端请求未认证」描述的鉴权能力在主路径上不存在。
- **修复**：将 pipeline 接入 `HandleClient`（推荐），或在分发前显式调用令牌校验并填充 `Auth`。同时删除/启用这批中间件，避免“看起来有鉴权”的误导。

### 4.3 🔴 目录心跳不校验签名——注册表可被任意投毒

- `HeartbeatHandler.HandleAsync`（`HeartbeatHandler.cs`）直接用请求体注册，**完全不读取/校验 `context.AccessToken`**。
- 这与 README §5「心跳签名：目录心跳…校验已严格化，签名缺失将拒绝」直接矛盾。
- **后果**：任何能连到 Directory 端口的主体都能注册/覆盖任意 `serverId` 的路由信息（路由劫持、把玩家导向恶意节点）。心跳令牌虽在发送端用 `ComposeHeartbeatToken` 生成，但服务端从不验证。
- **修复**：在 `HeartbeatHandler` 中用 `TokenSigner.TryVerifyHeartbeat(context.AccessToken, request.ServerId, secret, ...)` 校验，失败返回 `accepted=false`。

### 4.4 🟠 Redis SSL / mTLS 配置项定义了但未生效

- `DirectoryOptions.RedisRegistryOptions` 定义了 `Ssl / SslHost / ValidateServerCertificate / ClientCertificate`（`DirectoryOptions.cs:15-31`）。
- 但 `Program.cs:131` 构造注册表时只传 `ConnectionString` 与 `CleanupIntervalSeconds`：
  ```csharp
  return new RedisServerRegistry(dirOpts.Registry.Redis.ConnectionString, dirOpts.Registry.Redis.CleanupIntervalSeconds);
  ```
- `RedisServerRegistry` 用裸 `ConnectionMultiplexer.ConnectAsync(connectionString)`，**忽略所有 SSL/证书选项**。README §6 宣称支持 `directory:registry:redis:ssl` 与 mTLS，实属未接线。
- **修复**：用 `ConfigurationOptions` 构造，把 Ssl/SslHost/证书选项注入；或在文档中明确移除该承诺。

## 5. 重要问题（质量 / 可维护性 / 性能）

### 5.1 🟠 测试已被整体删除，覆盖率归零
当前工作区 git 状态显示 `tests/Tests/Tests.csproj`、`TokenSignerTests.cs`、`TimeManagerTests.cs`、`ErrorCodeMapperTests.cs` 全部 **deleted**，解决方案不再包含测试项目。上面 §4.1/§4.2 这类回归恰恰是单元/集成测试最容易锁定的。**强烈建议恢复测试项目并为协议编解码、TokenSigner、心跳往返补集成测试**。

### 5.2 🟠 重复的健康检查 HTTP 服务器
- `ServerHost/Program.cs` 已通过 `WebApplication` 在 `healthCheckUrl` 上暴露 `/health`、`/ready`、`/admin/command`、`/api/routing/query`。
- 但 `BaseGameServer.StartAsync`（`BaseGameServer.cs:156-174`）又**为每个 server 实例额外起一个 Kestrel `WebHost`**，监听 `port + 10000`，仅服务 `/health`。
- `--service all` 模式下会额外拉起 4 个 Kestrel（15500/15501/15502/15503），与主应用的健康端点重复，浪费端口与资源，关停路径也更复杂。
- **修复**：删除 `BaseGameServer` 内嵌的 WebHost，统一由宿主的 ASP.NET 健康检查负责。

### 5.3 🟡 文档与配置实现脱节
- README §1.3 声称「不再读取任何环境变量」，但 §5/§6 与 `doc/COMMANDS.md` 又依赖 `TOKEN_SECRET`、`TOKEN_TIME_SKEW_SEC`、`ADMIN_HTTP_ENABLED`、`ADMIN_TOKEN`、`ADMIN_HTTP_ALLOWED_IPS`、`DIRECTORY_TOKEN_SECRET`、`REDIS_PASSWORD`。`Program.cs:200/207/212` 实际仍通过 `IConfiguration` 读取这些键（可由环境变量提供）。**自相矛盾，需统一口径**。
- `TokenSigner.GetAllowedSkewSeconds()`（`TokenSigner.cs:60`）**硬编码返回 60**，但 README 多处称 `TOKEN_TIME_SKEW_SEC` 可配置。编译告警 `S3400` 也指向此处。**应改为从配置读取或修正文档**。

### 5.4 🟡 RoundRobin 选择策略实际失效
`ServerSelectionStrategyFactory.Create` 在**每次请求**都 `new RoundRobinStrategy()`（`ServerQueryHandler.cs:10`），而 `RoundRobinStrategy._counter` 是实例字段，每次都从 0 开始 → `offset` 恒为 1 → 无法跨请求轮询。**修复**：将策略实例缓存为单例（按策略名复用），让计数器跨请求保持。

### 5.5 🟡 每连接限流的黑名单按 `IP:port` 记录，对重连无效
`CheckByteRateLimit`/`CheckMessageRateLimit` 在每连接限速触发时调用 `AddToBlacklist(remoteEndpoint, ...)`，而 `remoteEndpoint` 是 `IP:port`（`BaseGameServer.cs:496/524`）。客户端重连会换临时端口 → 黑名单项永不再命中。只有 IP 级限速用了 `remoteIpOnly`。**建议每连接限速也按 IP 拉黑**（或明确区分两种语义）。

### 5.6 🟡 反射驱动的响应状态判定
`HandlerInvoker.DetermineStatusAndCode`（`MessageHandling.cs:66`）用反射读取响应的 `Success/Code/Message` 属性来判定成败。虽缓存了 `PropertyInfo`，但每次响应仍 `GetValue`，且**强依赖命名约定**，脆弱。**建议**引入显式响应契约（接口或基类 `IServerResponse { bool Success; int Code; string Message; }`），消除反射。

### 5.7 🟡 热路径上的逐消息分配
`HandleClient` 每条消息分配 `new byte[4]` 与 `new byte[length]`（`BaseGameServer.cs:580/590`），高并发下 GC 压力明显。**建议**使用 `ArrayPool<byte>` 或 `System.IO.Pipelines` 重写读路径。Unbounded Channel 也缺乏背压，慢消费时可能内存膨胀（与限流叠加考虑）。

## 7. 工程优点（值得保留）

- **清晰的分层**：Shared（协议/原语）→ Core（框架）→ ServerHost（宿主）职责分明。
- **生产化脚手架齐全**：OpenTelemetry、健康检查、k8s 全套清单（HPA/PDB/NetworkPolicy/Sentinel）、docker-compose。
- **可插拔设计**：注册表（内存/Redis）、选择策略工厂、组件生命周期（`InitializeAsync/DestroyAsync`）。
- **可测试的时间抽象**：`TimeManager` 支持系统/偏移/手动三模式，便于令牌过期等逻辑测试。
- **安全细节到位之处**：HMAC-SHA256 签名 + `CryptographicOperations.FixedTimeEquals` 定时比较、令牌撤销列表、限流 + 黑名单框架。
- **运维友好**：控制台 REPL + HTTP `/admin/command` 双通道命令系统，生产端有 Bearer + IP 白名单保护。
