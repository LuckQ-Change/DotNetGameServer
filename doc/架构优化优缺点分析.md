# LoginServer 作为唯一门户的架构分析

## 架构对比

```
当前架构（4个对外入口）                    优化架构（1个对外入口）

Client ──── LoginServer(5501)              Client ──── LoginServer(5501) ─ 唯一门户
     │                                       │
     ├── LogicServer(5502)                    ├── 消息总线 ── LogicServer(内部)
     │                                        │
     ├── BattleServer(5503)                   ├── 消息总线 ── BattleServer(内部)
     │                                        │
     └── DirectoryServer(5500)                └── 消息总线 ── DirectoryServer(内部)
```

---

## 优点

### 1. 安全性提升
- **消除攻击面**：3 个内部服务器不暴露公网端口，无法被直接扫描或攻击
- **统一鉴权**：所有客户端请求必须经过 LoginServer 的 Token 验证，杜绝绕过登录
- **流量审计**：所有进入流量集中经过 LoginServer，便于日志审计和异常检测
- **网络隔离**：内部服务器可部署在私有子网，仅 LoginServer 在 DMZ

### 2. 运维简化
- **单一入口**：DNS 只需一个域名，负载均衡只需一个 VIP
- **集中限流**：在 LoginServer 一层做全局限流和黑名单，不需要每个服务各自维护
- **无缝扩容**：新增 Logic/Battle 实例无需更新客户端配置，LoginServer 动态发现即可
- **灰度发布**：可按比例将流量路由到新版/旧版服务器，实现零停机发布

### 3. 客户端简化
- **连接数减少**：客户端从连接多个服务器简化为只连一个
- **逻辑下沉**：路由选择逻辑从客户端移到服务端，客户端无需知晓内部分布
- **断线重连**：只需重连 LoginServer，服务端透明恢复会话路由
- **协议升级**：内部协议变更不影响客户端，LoginServer 充当适配层

### 4. 架构清晰
- **关注点分离**：LoginServer 专注认证和路由，Logic/Battle 专注业务逻辑
- **可观察性强**：LoginServer 成为观测点，便于收集全局指标（QPS、延迟、错误率）
- **服务网格化**：为后续引入 Service Mesh（如 Istio）奠定基础

## 缺点

### 1. LoginServer 成为单点瓶颈

| 维度 | 风险 | 影响 |
|------|------|------|
| **吞吐量** | 所有客户端流量汇聚，LoginServer 带宽和 CPU 压力倍增 | 可能成为性能瓶颈，需水平扩展 LoginServer 集群 |
| **可用性** | LoginServer 宕机 = 全部不可用 | 原本 Login 挂掉不影响已连接的 Logic 连接 |
| **内存** | 维护所有客户端会话和路由表 | 万人同时在线时内存占用大 |

**缓解**：LoginServer 集群部署 + 前端负载均衡（Nginx/HAProxy），会话状态外置到 Redis。

### 2. 额外网络延迟

```
原架构：Client → LogicServer（1跳）
新架构：Client → LoginServer → 消息总线 → LogicServer（2-3跳）
```

- 每条消息多一跳转发，增加 0.5-2ms 延迟
- 对延迟敏感型游戏（FPS、格斗）影响较大
- 消息总线的序列化/反序列化也有 CPU 开销

**缓解**：LoginServer 和内部服务部署在同一机房/可用区；采用零拷贝转发减少序列化开销。

### 3. 实现复杂度上升

| 新增模块 | 复杂度 |
|----------|--------|
| 消息总线（Redis Pub/Sub 或 gRPC） | 部署、运维、监控 |
| LoginRouter 路由决策引擎 | 路由算法、会话亲和性、故障转移 |
| 服务发现增强 | 实时监控每个后端实例的状态 |
| 双向消息转发 | 请求和响应都需要通过 LoginServer 中转 |
| 错误处理 | 后端故障时 LoginServer 需要清理会话并通知客户端 |

### 4. 调试和排障变难

- **链路变长**：追踪一条消息需要跨越 LoginServer → 消息总线 → 后端服务器
- **会话状态分散**：LoginServer 和后端服务器各维护部分状态，数据不一致风险
- **日志关联**：需要分布式追踪（OpenTelemetry）才能串联请求链路
- **复现困难**：旧架构本地单进程就能复现问题，新架构至少需要启动 3 个服务

### 5. 原有设计资产浪费

- `BaseGameServer` 的 TCP 监听、限流、黑名单能力在内部服务器上不再直接使用
- `scripts/start-all.ps1` 的多窗口启动脚本需要重写
- `docker-compose.yml` 和 `k8s/` 配置需要大幅调整
- 现有客户端 SDK 需要重构连接模型

## 折中方案

如果对完全推到重来有所顾虑，可以采用渐进式的混合模式：

### 混合方案：LoginServer 直接代理

```
Client ──── LoginServer(5501)
                │
                ├── TCP 直连 ── LogicServer(内部网络，无公网 IP)
                │
                └── TCP 直连 ── BattleServer(内部网络，无公网 IP)
```

- **不做消息总线**，LoginServer 建立到后端服务器的 TCP 长连接池
- 无需引入新的中间件（Redis/RabbitMQ/gRPC 流）
- 延迟更低（无序列化转发层），但 LoginServer 代码复杂度更高
- 适合中小规模、延迟敏感的场景

### 混合方案：LoginServer 只做握手

```
Client ──── LoginServer(5501)
                │
                │  握手阶段：认证 + 分配服务器地址
                │
                └── 返回 LogicServer/BattleServer 的内部地址

Client ──── LogicServer(内部地址)  ← 后续通信直连后端
```

- LoginServer 只负责认证和路由决策，不转发业务消息
- 后续客户端直连后端，保持低延迟
- 需要客户端支持双连接模型（认证连接 + 业务连接）
- 后端服务器仍需要对外暴露（但可以通过防火墙限制仅信任客户端 IP）

---

## 决策矩阵

| 维度 | 当前架构 | 全代理方案 | 混合(握手)方案 | 混合(直连)方案 |
|------|----------|------------|----------------|----------------|
| **安全性** | 低（4个攻击面） | 高 | 中高 | 中 |
| **性能延迟** | 最优 | 有额外开销 | 中 | 较优 |
| **实现复杂度** | 低 | 高 | 中 | 中高 |
| **运维复杂度** | 高 | 中 | 中 | 中 |
| **客户端改动** | 无 | 大 | 中 | 中 |
| **扩展性** | 差 | 好 | 好 | 好 |
| **故障隔离** | 好 | 差（Login 挂全挂） | 中 | 好 |

---

## 建议

如果项目处于**早期开发阶段**、玩家规模预计在 **千人以内**，建议采用**混合(握手)方案**：LoginServer 负责认证和路由，业务流量直连后端，降低延迟同时保留扩展性。

如果项目目标是**万人以上大规模运营**，建议采用**全代理方案**：集中管理、安全可控、便于运维，但要做好 LoginServer 集群化和性能压测。

---

## 最终建议

| 场景 | 推荐方案 |
|------|----------|
| 开发/测试阶段 | 保持当前架构，逐步向混合方案过渡 |
| 中小规模上线 | 混合(握手)方案：Login认证+路由，业务直连 |
| 大规模运营 | 全代理方案：Login统一转发，集群化部署
