# 项目命名规则

适用于 DotNetGameServer 仓库中的所有解决方案、项目、目录、文件、代码元素、配置、基础设施与发布制品。目标是：统一、可读、可搜索、可维护，并与现有结构保持一致。

## 通用原则
- 统一英文命名，必要时在代码或文档中提供中文注释。
- 语义清晰，避免缩写与拼音；不得使用魔法字符串（参见《编码规范-禁止魔法字符串.md》）。
- 使用 `PascalCase`（大驼峰）命名公共类型与成员；使用 `camelCase`（小驼峰）命名本地变量与参数。
- 命名表达“是什么”和“用来做什么”，避免与实现细节强耦合。
- 保持与现有仓库目录、项目名和命名空间对齐。

## 解决方案与项目
- 解决方案（`.sln`）：使用产品根名，如 `DotNetGameServer.sln`。
- 项目（`.csproj`）：
  - 服务器类项目：`<RoleName>Server`，如 `LoginServer`、`ResourceServer`、`BattleServer`、`DirectoryServer`、`LogicServer`。
  - 宿主入口：`ServerHost`。
  - 核心库：`Core`；共享库：`Shared`；管理后台：`AdminPanel`。
  - 测试项目：`<ProjectName>.Tests`（若引入单元测试）。
- 项目目录：统一位于 `src/<ProjectName>/`。

## 目录与文件
- 目录：`PascalCase`，按职责分层：`Components`、`Handlers`、`Models`、`Config`、`Ecs` 等。
- C# 源文件：一个公共类型一个文件，文件名与类型名一致（`PascalCase`）。
- 配置文件：`appsettings.json`、`appsettings.Development.json`、`appsettings.Staging.json`、`appsettings.Production.json`。
- 文档：位于 `docs/`，中文文档命名使用简体中文标题（如本文件）。

## 命名空间与类型
- 命名空间：`DotNetGameServer.<ProjectName>.<Area>`，示例：`DotNetGameServer.ResourceServer.Components`。
- 接口：`I` 前缀（如 `IServerComponent`）。
- 抽象/基类：`Base` 后缀（如 `BaseGameServer`），或 `Abstract`（视语义选择）。
- 组件：`Component` 后缀（与 `Components` 目录对应）。
- 处理器：`Handler` 后缀（与 `Handlers` 目录对应）。
- 配置/选项类：`*Options` 或 `*Settings`（用于绑定 `appsettings`）。
- DTO/消息：`Record` 或 `Class`，保持 `PascalCase`，避免后缀泛滥（除非必要区分如 `Request`/`Response`）。

## 成员命名
- 类/结构/枚举/委托/属性/方法：`PascalCase`。
- 字段：私有字段使用前缀 `_camelCase`；公共字段使用 `PascalCase`（谨慎使用公共字段）。
- 局部变量与参数：`camelCase`。
- 常量：`PascalCase`，优先 `static readonly` 表示不可变数据；枚举成员使用 `PascalCase`。
- 泛型类型参数：`T` 前缀，如 `TRequest`、`TResponse`。

## 特定约定
- 异步方法：`*Async` 后缀（如 `LoadResourcesAsync`）。
- 事件：使用过去式或状态变化语义，如 `ResourceLoaded`、`StateChanged`；事件参数类型以 `EventArgs` 后缀或派生自其。
- 处理器/服务命名：使用动宾结构体现职责，如 `LoginHandler`、`TokenSigner`、`ErrorCodeMapper`。
- Protobuf（`Shared/Protos`）：消息、服务、枚举使用 `PascalCase`；字段使用 `snake_case`（与 Proto 社区约定对齐）；生成的 C# 类型遵循 C# 规范。

## 资源与配置
- 资源清单：遵循《资源清单规范.md》，资源键使用可读、分层的键名：`feature.subfeature.item`。
- 配置键：以分层结构命名，如 `Redis:Endpoints`、`Auth:TokenLifetimeMinutes`；避免魔法字符串，集中管理键名（常量或选项类）。
- 环境变量：全部大写并使用下划线分隔，如 `ASPNETCORE_ENVIRONMENT`、`REDIS_PASSWORD`。

## 数据库对象（如使用 MySQL）
- 数据库/模式：`snake_case`，避免大小写敏感问题。
- 表：复数形式 `snake_case`（如 `user_tokens`）；主键一般使用 `id` 或复合键；外键命名为 `<referenced_table>_id`。
- 列：`snake_case`，布尔列使用 `is_` 前缀（如 `is_active`）。
- 索引：`idx_<table>_<columns>`；唯一约束：`uq_<table>_<columns>`。

## Git、CI/CD 与容器
- 分支：`feature/<short-kebab>`、`fix/<short-kebab>`、`chore/<short-kebab>`、`release/<version>`。
- 标签：`v<major>.<minor>.<patch>`（如 `v1.2.0`）。
- Docker 镜像：`dotnetgameserver/<component>:<tag>`，如 `dotnetgameserver/serverhost:v1.2.0`。
- Kubernetes 资源：使用 `kebab-case` 与明确后缀，示例：`serverhost-deployment`、`serverhost-service`、`redis-sentinel`。

## 版本与环境
- 环境名：`Development`、`Staging`、`Production`（与 `appsettings.*.json` 对齐）。
- 兼容性声明：在文档与变更日志中记录面向客户端/服务间协议版本变更。

## 与现有仓库对齐的示例
- 类型与文件：`BaseGameServer.cs`、`ResourceGameServer.cs`、`ErrorCodeMapper.cs`、`TokenSigner.cs`。
- 目录：`src/ResourceServer/Handlers`、`src/Core/Components`、`src/ServerHost/HealthChecks`。
- 命名空间：`DotNetGameServer.Core.Logging`、`DotNetGameServer.LoginServer.SignIn`。
